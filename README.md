تنفيذ SQLite مع تطبيق Flutter عربي يعمل محليًا، ومحرك ترحيل واحد داخل SQL تستعمله اختبارات Python والتطبيق عبر `sqflite`. حُفظت مخططات `docs/00` إلى `docs/12` كما هي، بناءً على المصدر `8bf595847791a6f4c03eda27ec2b711dad07e8a6`.

**تحديث 2026-11-12:** نجح التحليل و8 اختبارات Flutter و58 اختبار SQLite واختبارا Android، ثم بناء APK وتثبيته وتشغيله وإعادة تشغيله على محاكي Android 13. [تنزيل APK مباشرة](https://github.com/lsrwrbdllh-dot/Accounting-System-ERD/releases/download/android-preview-15-d679c1efdec73eed7e104103eccdb23187e049dc/Accounting-System-Android.apk) — [تقرير الإصلاح والتثبيت](reports/ANDROID_INSTALLATION_REPORT.md). النسخة Preview ببيانات تجربة وتوقيع اختبار؛ لم تُجرب على Redmi 12 فعليًا.

## تشغيل قاعدة البيانات والاختبارات الآن

يلزم Python 3.12+ مع SQLite؛ لا تحتاج الاختبارات إلى حزم إضافية.

```bash
python3 tools/verify.py
python3 -m database.cli init /tmp/accounting_demo.db --demo
python3 -m database.cli check /tmp/accounting_demo.db
```

للإنتاج، أنشئ ملفًا آخر. كلمة المرور تُطلب دون عرضها أو تمريرها في سطر الأوامر:

```bash
python3 -m database.cli init /tmp/accounting_production.db --admin owner
```

يمكن أيضًا إنشاء قاعدة إنتاج جديدة بتنفيذ `database/schema.sql` عبر SQLite. هذا الملف مولّد ويحتوي سجل التحديثات؛ القواعد الموجودة تُحدّث عبر runner ولا يعاد إنشاء جداولها. مثال عند وجود برنامج sqlite3:

```bash
sqlite3 accounting_production.db < database/schema.sql
```

`database/runtime.py` أداة تشغيل واختبار محلية؛ جميع آثار الترحيل المالية موجودة في SQL نفسه، وليست محاكاة منفصلة لمنطق Flutter.

## تشغيل تطبيق Android خارج البيئة الحالية

1. ثبّت Flutter **3.38.0** وAndroid Studio، مع Android SDK وCommand-line Tools وPlatform Tools. استخدم JDK 17 المتوافق مع إعدادات المشروع، وثبّت منصات SDK التي يطلبها `flutter doctor` والبناء.
2. أنشئ جهازًا افتراضيًا من Android Studio Device Manager وشغّله، أو صِل هاتفًا حقيقيًا مع USB debugging. APK المبني بـFlutter 3.38 يتطلب Android 7 / API 24 فأعلى، كما تؤكد معلومات الحزمة الفعلية؛ ترفع أداة Flutter القيمة 23 الموجودة في مصدر Gradle أثناء البناء.
3. من جذر المستودع، نفّذ:

```bash
python3 tools/build_assets.py
cd app
flutter doctor -v
flutter doctor --android-licenses
flutter pub get
flutter analyze
flutter test
flutter devices
flutter run --dart-define=APP_ENV=demo -d emulator-5554
```

استبدل `emulator-5554` بمعرّف الجهاز الحقيقي من `flutter devices`. ويمكن تشغيل محاكي مُعدّ مسبقًا بواسطة `flutter emulators` ثم `flutter emulators --launch <emulator_id>`.

حساب التجربة: **demo** وكلمة المرور **Demo@2026!**. هذا حساب تجريبي معروف، بصلاحيات قراءة وحفظ وترحيل، دون إدارة المستخدمين. قاعدة التجربة `accounting_demo.db` منفصلة عن `accounting_production.db`. تشغيل الإنتاج:

```bash
flutter run --dart-define=APP_ENV=production -d emulator-5554
```

عند أول تشغيل للإنتاج تظهر شاشة إنشاء المدير؛ لا يوجد حساب أو كلمة مرور إنتاج افتراضية. دليل الحسابات والوحدات والصندوق والمستودع والسنة والفترة تنشأ دون أصناف أو عملاء تجريبيين. يمكن إضافة العميل/المورد من محرّر الفاتورة مع حساب فرعي مرتبط تلقائيًا، وإضافة الأصناف والوحدات من دليل الأصناف.

إنشاء APK تجريبي بعد نجاح التحليل والاختبارات:

```bash
flutter build apk --debug --dart-define=APP_ENV=demo
```

المسار الناتج `app/build/app/outputs/flutter-apk/app-debug.apk`، وحزمة Debug هي `com.accounting.system.diagnostic`. رابط التنزيل أعلاه يوزع APK مبنيًا بوضع Release، بحزمة `com.accounting.system.preview` واسم «النظام المحاسبي - تجربة». يُبنى باستخدام `flutter build apk --release --dart-define=APP_ENV=demo` ثم يوجد في `app/build/app/outputs/flutter-apk/app-release.apk`. النسخة موقعة بمفتاح اختبار؛ يلزم مفتاح مملوك محفوظ في GitHub Secrets قبل الإنتاج وضمان التحديثات المستقبلية دون تعارض توقيع. لا تحذف نسخة تحتوي بيانات لمعالجة تعارض توقيع. ملف `pubspec.lock` مطابق للحزم المستخدمة في التحقق الناجح.

## تجربة الشاشات واستمرار الحفظ

التطبيق يحتوي الدخول/إعداد المدير، لوحة ملخصات، الحسابات، الأصناف والوحدات، البيع والشراء والمرتجعات، سندات القبض والصرف، القيود والمخزون. تدعم الأدلة الإضافة والتعديل والبحث. تدعم المستندات حفظ وتعديل المسودة وعرض التفاصيل والبحث والترحيل؛ المستند المرحّل محمي من التعديل.

في بيئة التجربة: احفظ مشتريات لصنف الحليب، ثم رحّلها من تفاصيل الفاتورة. احفظ مبيعات ثم رحّلها، وراجع المخزون والحسابات. المرتجعات متاحة من قائمة نوع الفاتورة أعلى الشاشة. اختر الأصل وسطره والكمية. للسداد الآجل، أنشئ فاتورة آجل مع عميل/مورد، ثم سندًا على حساب الطرف وخصص السداد لفاتورة أو أكثر.

اختبار تكامل Android مرفق؛ يستخدم قاعدة مستقلة يمسحها بعد الاختبار:

```bash
flutter test integration_test/persistence_test.dart -d emulator-5554
```

اجتاز الاختباران المحاكي: القراءة وتعديل المسودة والترحيل وإعادة فتح SQLite، ثم الدخول وحفظ فاتورة مشتريات وترحيلها ومراجعة المخزون عبر الواجهة. فحصت CI أيضًا تثبيت APK بوضع Release وإيقاف عمليته وإعادة إطلاقها، مع لقطة شاشة للدخول. للتحقق يدويًا من بقاء فاتورة بين عمليتين منفصلتين، احفظ مسودة برقم معروف، ثم:

```bash
adb shell am force-stop com.accounting.system.preview
adb shell monkey -p com.accounting.system.preview 1
adb logcat -d -s flutter AndroidRuntime
```

سجّل الدخول وتحقق من بقاء المسودة والتعديل ورصيد المخزون. فحص بقاء فاتورة بين عمليتين منفصلتين **لم ينفذ هنا**؛ اختبار الحفظ الآلي يفتح اتصال SQLite من جديد. استعمل `.diagnostic` بدل `.preview` عند تشغيل نسخة Debug.

## قواعد المحاسبة

- النوع 1 مشتريات، 2 مبيعات، 3 مردود مبيعات، 4 مردود مشتريات، **5 صرف، 6 قبض**، 7 قيد يدوي.
- حفظ المسودة لا يؤثر على الأرصدة. تغيير الحالة إلى `Posted` يستدعي تحقق SQL وتسجيل الحركة والتكلفة والقيد والتدقيق داخل المعاملة نفسها. فشل أي خطوة يعيد الجميع، حتى عند الترحيل بـSQL مباشر.
- القيود تحتاج طرفين صالحين على الأقل ومجموع مدين يساوي مجموع دائن. تُمنع الحسابات التجميعية وغير النشطة، كما يُمنع القيد اليدوي على حساب المخزون.
- الأموال أعداد صحيحة بأصغر وحدة نقدية: `100 = 1.00`. الكمية والتعبئة بوحدة `1000 = 1.000`. الإدخال والتحويل لا يستعملان `double`.
- التقريب إلى أقرب وحدة نقدية بنصف لأعلى. تكلفة المخزون متوسط متحرك لكل مستودع/صنف/دفعة. توزّع فروق التقريب تراكميًا؛ مردود البيع يعكس تكلفة البيع الأصلية، ومردود الشراء يستعمل القيمة الدفترية الحالية مع حساب فرق التكلفة.
- المرتجع مرتبط بأصل مرحّل وبسطره ولا يتجاوز كميته. يتبع نفس المستودع والطرف وطريقة السداد. مردود الآجل لا يتجاوز الجزء غير المسدد. رد قيمة فاتورة آجلة مسددة يتطلب مسار استرداد مستقل غير منفذ هنا؛ العملية تُرفض بدل توليد تسوية خاطئة.
- يمنع المخزون السالب، وتُمنع الحركة بتاريخ أقدم من آخر ترحيل في المستودع. الأرصدة الافتتاحية المالية تسجل بقيد يدوي متوازن، ولا تُجمع مرة أخرى من جدول `AccountOpeningBalances`.
- حد المبلغ لكل مستند/سطر `1,000,000,000` وحدة نقدية صغرى، وحد رصيد الكمية الأساسية `1,000,000,000` جزء من ألف. تمنع الحدود تجاوز حسابات INTEGER ذات 64 بت.
- لا تتجاوز تخصيصات السداد مبلغ السند أو رصيد الفاتورة بعد المرتجعات، ويلزم تطابق نوع السداد وحساب الطرف. المسودات غير المرحّلة لا تخصم من الرصيد.
- تدعم النسخة التشغيلية عملة أساسية بدقتين عشريتين وسعر `1.000000`. جداول العملات وأسعارها موجودة للتوسع، وتُرفض حاليًا مستندات العملة الأجنبية صراحة.

## التحديثات والملفات

`database/migrations/001_schema.sql` ينشئ الجداول، و`002_integrity_posting.sql` ينشئ الحمايات والعروض ومحرك الترحيل. يطبّق runner كل تحديث في transaction ويسجل SHA-256 ويرفض تخفيض الإصدار أو تعديل تحديث مطبّق. تُفعّل المفاتيح الأجنبية عند **كل اتصال** في Python وFlutter.

أضف ملفات تحديث متتالية جديدة، ولا تعدّل تحديثًا مطبّقًا. لتحديث الحزمة المضمّنة في Flutter والملف الموحد:

```bash
python3 tools/build_assets.py
python3 tools/verify.py
```

`tools/generate_integrity.py` مصدر توليد مشغلات الإصدار الثاني أثناء تطوير هذه النسخة. بعد نشرها تُجرى التغييرات بتحديث جديد. ملفات SQL هي مصدر المنطق المشترك. لا تقسّم SQL على `;`؛ الحزمة JSON تحفظ كل مشغّل كتعليمة واحدة.

النسخة القديمة غير المرقمة محفوظة في `database/legacy`. لا توجد قاعدة مستخدم قديمة في المستودع. عند اكتشاف قاعدة غير مرقمة يرفض runner فتحها كتحديث دون مساس ببياناتها؛ تحويلها يحتاج نسخًا احتياطيًا ومطابقة الأرصدة ووحدات القياس، ولم يُدّع تنفيذ محوّل تلقائي لها.
